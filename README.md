# SCM Shipment Control Tower

판매계획, 생산·선적 물량, ERP 확인과 변경 출처를 한곳에서 추적하기 위한 SCM 웹사이트입니다. 업무 요구사항의 원본은 [docs/README.md](docs/README.md)이며, 현재 화면은 모두 **합성 데이터 데모**입니다.

## 현재 완성된 범위

- Next.js·TypeScript 화면과 FastAPI API
- 로컬 PostgreSQL 16.15 저장소와 Alembic 마이그레이션
- 로그인 사용자의 프로젝트 목록, 빈 프로젝트 생성, 현재 상태 사본 생성과 프로젝트 영구 삭제
- 판매법인별 매출 흐름 대시보드와 Sales Master의 합성 주문 조회
- 기존 업무 화면과 분리된 정적 예시 BuildLog 운영 대시보드(`/dashboard`)
- 모든 화면에 공통 적용되는 연두·검정·회색 중심의 업무용 색상 체계
- XLSX·XLS·CSV 판매자료 업로드, 시트·헤더 선택, 규칙 기반 및 선택형 AI 보조 컬럼 매핑
- 행별 검증, 통화별 수량·금액 대사, 최초 자료의 Sales Master 반영
- 원본 파일·원본 행·표준화 결과·법인별 매핑 보존과 중복 반영 방지
- 판매법인 9곳, 생산법인 6곳 기준정보와 부분 생산·선적·ERP 미확인·매칭 검토 사례
- Sales Master 전체 열의 검색·선택형 필터, 수량 옆 Unit Price (USD), Net/Gross USD 분리, 필터 결과 수량·금액 합계
- Sales Master의 모델·고객 분리, 목록 맨 위 합계, 생산·선적 예정일·완료·미완료·다음 일정·이월 가능 수량 표시
- 상단 우측에서 프로젝트 기준 날짜를 저장하고, 그 날짜보다 과거인 PST·ETD 물량의 생산·선적 상태를 화면과 Excel에서 다시 계산
- Sales Master 주문·생산·선적 상세 수동 수정, 수동값 우선 보존과 후속 판매파일의 선택형 업데이트 검토
- 대시보드 전체 합계 맨 위 표시와 실제 숫자가 포함된 Excel 합계 행
- 현재 월 기준 과거 3개월·현재 월·미래 8개월의 주차별 PSI 표(DM·SA·SP·Inventory·Warehouse)
- PSI XLSX 신규 업로드, 기준월·등록자·버전 이력 보존, 최근 승인본 대비 주차별 증감 비교와 승인
- 기준 주차까지 누적 DM 대비 SA 부족, SA 대비 SP 지연을 보여 주는 RISK 검토 신호
- PSI의 판매법인·생산법인·모델을 모든 지표 행에 반복 표시
- PSI RISK 후보 주문을 사용자가 선택해 승인·보류하고 승인 근거를 Sales Master RISK에 표시
- 판매계획·PSI·생산정보·선적정보 업로드의 영구 삭제와 같은 파일 재업로드 시 최신 정보 덮어쓰기
- 대시보드, Sales Master, PSI의 실제 Excel 다운로드
- Sales Master의 합성 주문 저장, 재조회 및 서버 재시작 후 보존
- 나머지 업무 메뉴의 역할 설명과 `준비 중` 표시

판매계획 주문 버전의 승인 반영 엔진, Gmail·실제 ERP 연동과 외부 배포는 아직 구현하지 않았습니다. 생산·선적정보는 PO·모델·행별 판매법인·가용수량이 안전하게 일치할 때 PST 또는 ETD 예정 물량을 자동 연결합니다. OpenAI 키가 설정된 경우 규칙으로 단일 주문을 찾지 못한 생산·선적 행에는 AI가 후보와 근거를 제안하지만 `검토 필요`로만 보존합니다. 양식이 달라진 후속 판매계획도 AI 후보는 Sales Master의 `업데이트 검토`에만 나타나며 주문을 자동 변경하지 않습니다.

## 확인된 개발 환경

Windows에서 Node.js `24.22.1`, npm `11.19.1`, Python `3.13.14`, Git `2.56.0.windows.3`을 확인했습니다. Docker CLI는 있으나 엔진은 실행되지 않았습니다. 프로젝트 안에 PostgreSQL `16.15` 실행 파일을 준비하여 시스템 설치 없이 `127.0.0.1:5433`에서 실제 연결을 검증했습니다.

프런트엔드는 Next.js `15.5.28`, React `19.1.7`, TypeScript `5.8.3`으로 고정되어 있습니다. Python 전체 잠금 버전은 `backend/requirements-lock.txt`에 기록했습니다.

## 처음 한 번 준비

VS Code에서 `SCM_Project` 폴더를 열고 PowerShell 터미널에서 실행합니다.

```powershell
python -m venv backend\.venv
backend\.venv\Scripts\python.exe -m pip install -r backend\requirements-lock.txt
cd frontend
npm.cmd ci
npm.cmd run build
cd ..
```

현재 PC에서는 위 의존성이 이미 준비되어 있습니다. `.env`에는 로컬 DB의 무작위 비밀번호가 들어 있으며 Git에서 제외됩니다. 비밀번호를 대화창이나 소스코드에 입력하지 마세요. `.env.example`은 변수 이름만 보여주는 예시입니다.

## 실행과 종료

프로젝트 루트의 PowerShell에서 다음 한 줄로 PostgreSQL, API, 화면을 시작합니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

브라우저에서 `http://127.0.0.1:3000`을 엽니다. 별도 BuildLog 예시 화면은 로그인 후 `http://127.0.0.1:3000/dashboard`에서 확인합니다. API 상태는 `http://127.0.0.1:8000/health`, API 문서는 `http://127.0.0.1:8000/docs`에서 확인할 수 있습니다.

종료할 때는 다음 명령을 실행합니다. 주문 데이터는 삭제되지 않습니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\stop.ps1
```

다시 시작할 때는 `start.ps1`을 다시 실행하면 됩니다. 시작에 실패하면 `.local/api-error.log`, `.local/web-error.log`, `.local/postgres.log`를 확인합니다.

### 프로젝트 만들기와 삭제

로그인 후 왼쪽의 `프로젝트 관리`를 누르면 접근 가능한 프로젝트 목록과 주문·업로드·PSI 건수를 확인할 수 있습니다. `빈 프로젝트 시작`은 기존 주문이나 업로드를 가져오지 않는 0건의 독립 작업공간을 만들고 바로 전환합니다. `사본 만들기`는 현재 프로젝트의 Sales Master 상태를 새 내부 ID로 복사합니다.

프로젝트 삭제는 소유자만 할 수 있으며 프로젝트 이름을 정확히 다시 입력해야 합니다. 삭제하면 해당 프로젝트의 주문·업로드·PSI·검토·변경 자료가 한 트랜잭션으로 영구 삭제되고 복구할 수 없습니다. 다른 프로젝트와 사본은 삭제하지 않으며, 공유 중인 원본 자료도 남깁니다. 계정이 사용할 수 없는 상태가 되지 않도록 마지막 프로젝트 한 개는 삭제할 수 없으므로 먼저 빈 프로젝트를 만들어야 합니다.

### 로그인 이메일 또는 비밀번호를 잊은 경우

프로젝트 루트의 VS Code PowerShell 터미널에서 다음 명령을 실행합니다. 등록된 이메일을 보여주고 새 비밀번호는 화면에 표시되지 않게 입력받습니다. 주문과 프로젝트 데이터는 삭제하지 않습니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\reset-password.ps1
```

새 비밀번호는 12자 이상 입력하고 확인을 위해 한 번 더 입력합니다. 변경이 끝나면 표시된 이메일과 새 비밀번호로 다시 로그인합니다.

## 판매자료 업로드 사용

브라우저에서 `http://127.0.0.1:3000/uploads`를 엽니다.

화면 맨 위에서 판매계획, 생산정보 또는 선적정보를 선택하고 파일·판매법인·자료 기준일·자료 범위·적용 범위를 입력합니다. 대상 월은 자료 기준일의 연·월로 자동 저장됩니다. 업로드한 원본은 아래 `전체 업로드 이력`에서 다시 다운로드할 수 있습니다. 메일·이미지·본문·붙여넣기 텍스트는 같은 화면의 별도 입력 영역을 사용합니다.

1. 자료 유형을 `판매계획`, `생산정보`, `선적정보` 중에서 선택합니다.
2. 파일과 자료 기준일, 전체 현황/변경분 및 적용 범위를 입력하고 `파일 업로드`를 누릅니다. 판매계획은 판매법인을 선택합니다. 생산·선적정보는 파일 내 여러 판매법인을 함께 처리하므로 판매법인 대신 파일을 보낸 생산법인을 토글로 선택합니다. 대상 월은 기준일에서 자동 표시됩니다.
3. 기본 생산법인은 이집트·인도네시아·구미가 먼저 표시됩니다. 필요한 법인이 없으면 같은 화면의 `법인 직접 추가`에서 판매법인 또는 생산법인을 현재 프로젝트에 추가합니다.
4. 메일 파일, 이미지, 메일 본문이나 복사한 텍스트도 같은 화면에서 등록할 수 있습니다.
   OpenAI 키가 연결되어 있으면 등록한 EML·HTML·TXT·붙여넣기 본문 또는 PNG·JPG·WEBP 이미지를 API가 읽어 PO·모델·수량·PST·ETD·ETA·선사·선박 등의 복수 업무 항목과 근거·신뢰도로 정리합니다. 이 입력 내용은 구조화 추출을 위해 OpenAI로 전송되며, 추출 결과는 검토용으로만 저장되고 Sales Master에는 자동 반영되지 않습니다.
5. 모든 등록 결과와 원본은 두 입력 영역 아래의 `전체 업로드 이력`에서 함께 확인하거나 다시 다운로드합니다. `입력 방식` 열에서 XLSX·CSV·메일·HTML·이미지·붙여넣기를 구분합니다.
6. 판매계획 파일은 이어서 가져올 시트와 헤더 행, 표준 컬럼, Net/Gross 단가·총액 구분을 확인합니다. 통화는 연결하지 않고 USD로 적용합니다. 저장 설정과 별칭이 먼저 자동 연결되며 서버의 `OPENAI_API_KEY`가 설정된 경우 미해결 컬럼명만 AI가 추가 추천합니다.
   판매계획에서는 생산사이트를 입력하지 않습니다. 생산계획을 Sales Master에 반영하면 이미 업로드한 생산정보의 PO·모델·행별 판매법인·수량을 다시 조회하여 후보가 하나이고 주문 잔량을 넘지 않을 때 생산법인과 PST 예정 물량을 자동 연결합니다. 애매하거나 수량이 충돌하는 행은 자동 확정하지 않습니다.
7. 행별 처리 결과와 USD 수량·금액 비교를 확인하고, 처리 불가 또는 확인 필요 항목이 없을 때 `Sales Master에 반영`합니다. AI 추천도 사람이 확인하기 전에는 반영되지 않습니다.
   처리 불가·확인 필요 행이 있으면 `확인이 필요한 원본 행`에서 실제 셀값과 사유를 확인할 수 있습니다. 합계·설명처럼 업무 데이터가 아닌 행은 `이 행 제외`를 눌러 제외하며, 원본과 제외 사유는 이력에 남고 해당 행은 수량·금액 대사와 Sales Master 반영에서 빠집니다. 실제 주문행은 제외하지 말고 매핑 또는 원본값을 바로잡아야 합니다.

판매계획 업로드 후 다른 작업을 했거나 화면을 다시 연 경우 `전체 업로드 이력`의 해당 파일에서 `Sales Master 매칭`을 누릅니다. 저장된 원본의 시트·헤더·컬럼 연결 단계가 다시 열리며, 반영 완료된 파일에는 중복 방지를 위해 버튼 대신 `매칭 처리 완료`가 표시됩니다.

AI 추천은 선택 기능입니다. 실제 키를 대화창이나 코드에 넣지 말고 프로젝트 루트의 `.env`를 VS Code에서 열어 `OPENAI_API_KEY=발급받은_키`로 설정합니다. 필요하면 `OPENAI_MAPPING_MODEL`, `OPENAI_MATCHING_MODEL`, `OPENAI_UNSTRUCTURED_MODEL`, `OPENAI_MATCH_MAX_ROWS`도 조정한 뒤 서버를 다시 시작합니다. 키가 없거나 호출에 실패해도 기존 규칙 기반 자동 연결과 수동 확인은 그대로 동작합니다. 키 연결 여부는 `연동 및 설정` 화면에만 표시되며 키 값은 API나 화면으로 보내지 않습니다.

`합계`, `Subtotal` 표시가 없는 중간 합계행은 AI 행 역할 분류와 서버의 수량·Net·Gross 합계 검증이 모두 일치할 때만 반영 대상에서 제외합니다. AI에는 실제 금액이나 원본 전체 행을 보내지 않고 누락 필드, 제한된 라벨, 합계 일치 여부만 보냅니다. API 키가 없거나 AI와 산술 검증 중 하나라도 불확실하면 일반 주문으로 조용히 반영하지 않고 확인 대상으로 유지합니다.

생산정보·선적정보에서 같은 유형의 같은 파일을 다시 올리면 같은 항목의 파일명·기준일·대상 월·등록시각·등록자·원본과 파싱 결과를 새 값으로 교체하고 `기존 항목을 최신 정보로 덮어썼습니다`라고 알립니다. 목록에는 같은 내용이 두 건 생기지 않습니다. 판매계획은 기존 중복 방지와 반영 절차를 그대로 사용합니다. 같은 법인·월에 이미 업로드 반영 주문이 있거나 기존 주문 여부가 모호하면 새 주문을 만들지 않고 `버전 비교 대기`로 보존합니다. 오류·검토 행이 하나라도 있으면 처리 행만 부분 반영하지 않습니다.

전체 업로드 이력에서는 판매계획·생산정보·선적정보를 모두 삭제할 수 있습니다. `삭제`를 누르면 파일명·자료 유형·기준일과 복구 불가 안내를 확인한 뒤 한 트랜잭션으로 영구 삭제하며 휴지통과 삭제 이력은 없습니다. 판매계획은 원본 파일·원본 행·표준화 결과·버전뿐 아니라 그 파일로 생성한 Sales Master 주문과 주문에 연결된 생산·선적 상세, ERP Closed, 수동 수정·변경 이력까지 함께 삭제합니다. 생산·선적정보를 삭제하면 그 원본에서 자동 생성한 확정 연결과 AI 검토 후보 연결도 제거하며, 수동 확정값과 다른 원본 연결은 보존합니다.

메일·이미지·붙여넣기 자료에서 생산정보와 선적정보가 한 원본에 함께 있으면 같은 원본을 두 번 사용할 수 있습니다. 먼저 `생산정보`로 저장하고, 자료 유형만 `선적정보`로 바꾸어 같은 원본을 다시 저장하세요. 같은 유형으로 반복하면 별도 항목을 만들지 않고 기존 항목을 최신 입력으로 덮어씁니다.

PSI도 같은 파일 해시를 다시 올리면 기존 버전을 최신 파일명·자료 기준일·기준월·등록자·등록시각·원본과 다시 파싱한 값으로 교체합니다. 변경된 기준일로 RISK를 다시 계산해야 하므로 덮어쓴 버전은 검토 상태에서 다시 시작합니다. PSI 버전을 영구 삭제하면 그 버전의 주차 값·RISK 검토·배분·변경 근거도 함께 없어지고, 이후 비교는 남은 가장 최근 승인본을 기준으로 자동 재계산됩니다.

## 데이터베이스 변경 관리

서버 시작 시 `alembic upgrade head`가 자동 적용됩니다. 모델 변경 후 새 마이그레이션은 백엔드 폴더에서 생성합니다.

```powershell
cd backend
.venv\Scripts\python.exe -m alembic revision --autogenerate -m "변경 설명"
.venv\Scripts\python.exe -m alembic upgrade head
```

기존 SQLite 데모 파일은 보존했지만 기본 실행에는 사용하지 않습니다. 논리 관계와 집계 규칙은 [데이터 모델](docs/data-model.md), 구현 상태는 [요구사항 추적표](docs/requirements.md), 실제 검증 결과는 [진행 기록](docs/progress.md)을 확인하세요.

Sales Master의 물류 일정은 PST(생산예정일)와 ETD(선적예정일)로 구분합니다. ETD에는 Shipment별 선사명과 선박명을 함께 표시합니다. ETA는 선사 자료에서 항상 제공되지 않아 현재 화면·업로드 매핑·API 응답·Excel 내보내기에서 사용하지 않으며 기존 DB 값만 호환을 위해 보존합니다.

Sales Master 주문의 `수정`을 누르면 SO·PO, 법인, 모델·고객, 수량·금액, Status와 생산·선적 상세를 직접 저장할 수 있습니다. 수동 저장한 값은 다음 파일보다 우선하며, 안전하게 같은 주문으로 식별된 후속 판매자료와 값이 다르면 주문 행에 `업데이트 검토` 버튼이 나타납니다. 비교 화면에서 선택한 필드만 새 파일 값으로 바뀝니다. 자동 업로드 일정은 프로젝트 기준 날짜보다 PST·ETD가 과거이면 완료로 표시하며 수동 확정값은 그대로 우선합니다.
