## 2026-11-06 과거 PST·ETD 생산·선적 완료 판정

- 현업 생산·선적계획에 별도 완료 플래그가 없다는 업무 규칙을 반영해, 프로젝트 기준 날짜보다 과거인 PST·ETD가 최신 파일에 유지되고 안전하게 매칭된 행은 해당 수량을 `실제 완료`·`실제 선적`으로 표시합니다.
- 기준 날짜 당일·미래 일정, AI 검토 후보와 모호한 주문 후보는 완료로 추정하지 않습니다.
- 완료로 확정한 과거 PST·ETD 물량은 후속 계획에서 그 행이 빠져도 보존하고, 같은 행이 다시 들어오면 중복 생성하지 않습니다.
- 자동 테스트에서 과거 PST 6ea·ETD 5ea의 실적 확정, 미래 일정 유지와 후속 누락 시 실적 보존을 확인했습니다. 기존 저장 자료도 같은 규칙으로 재판정해 생산 상세 16개와 선적 상세 12개를 완료로 전환했습니다. `20261114 SCM 프로세스 관리프로젝트`의 PO `0006112`는 생산·선적 모두 완료 24ea·미완료 0ea로 확인했습니다.
- 생산·선적 전체 완료 행은 Sales Master 일정 카드에서 `예정일 미정`과 `다음 일정 미정` 대신 `생산완료`·`선적완료`와 `추가 일정 없음`을 표시합니다. Next.js 프로덕션 빌드를 통과했습니다.
- 기존 종합 검증 스크립트 `verify_sales_master_improvements.py`는 이번 생산 규칙과 무관한 판매계획 `application_mode` 환경 의존 기대값에서 중단되어 전체 통과로 기록하지 않습니다. 생산 규칙 전용 검증과 실제 주문 재조회는 통과했습니다.

## 2026-11-05 OpenAI 컬럼·주문 후보 추천과 선적 자동 연결

- `.env`의 `OPENAI_API_KEY`를 서버에서만 읽고 키 값은 화면·API·로그에 노출하지 않습니다. `OPENAI_MAPPING_MODEL`과 `OPENAI_MATCHING_MODEL`을 분리하고 파일별 AI 후보 요청 상한을 `OPENAI_MATCH_MAX_ROWS`로 설정했습니다.
- 저장 매핑과 명시적 별칭을 먼저 사용하고 미해결 헤더명만 Responses API Structured Outputs로 보냅니다. 원본 파일·원본 전체 행·금액은 보내지 않습니다.
- 생산·선적 행이 규칙으로 유일하게 연결되지 않으면 표준화된 PO·모델·판매법인·고객·대상 월·수량과 프로젝트 내부 후보만 AI에 보내 후보와 근거를 받습니다. AI 추천은 `검토 필요` Allocation으로만 저장하고 수량·생산법인·실적을 자동 확정하지 않습니다.
- 선적정보도 생산정보와 같은 공통 처리 구조로 연결하며 ETD·ETA·선사·선박을 Shipment 상세에 저장합니다. 같은 원본 재처리는 그 원본의 비수동 연결만 교체합니다.
- 실제 PostgreSQL 트랜잭션에서 생산 6+4와 선적 5+5가 주문수량을 초과하지 않고 각각 연결되는지, AI 모의 추천은 생산 연결을 검토 상태로만 만들고 생산법인을 확정하지 않는지 확인했습니다. 양식이 달라진 후속 판매계획의 AI 모의 추천도 `업데이트 검토`만 만들며 기존 PO·수량을 자동 변경하지 않는 것을 확인했습니다. 실제 OpenAI 호출은 로컬 키가 설정되지 않아 미검증입니다.
- `합계` 문구가 없는 중간 합계도 읽을 수 있도록 AI 행 역할 분류를 추가했습니다. AI에는 실제 금액 대신 서버의 합계 일치 여부만 보내며, AI 분류와 수량·금액 산술 검증이 모두 일치할 때만 제외합니다. 모의 AI로 일반 검증 파일과 현재 튀르키예 파일을 다시 계산해 튀르키예 파일이 처리 8행·제외 5행·오류 0행이 되는 것을 확인했습니다. 실제 OpenAI 호출은 키 미설정으로 미검증입니다.

## 2026-11-06 메일·줄글·이미지 OpenAI 구조화 추출

- EML·HTML·TXT·붙여넣기 본문은 Responses API의 텍스트 입력, PNG·JPG·WEBP는 이미지 입력으로 보내도록 구현했습니다.
- 판매계획·생산정보·선적정보별로 PO·모델·고객·수량·USD 금액·법인·PST·ETD·ETA·선사·선박을 여러 레코드로 추출하고 각 레코드의 근거와 신뢰도를 저장·표시합니다.
- AI 결과는 검토용이며 Sales Master에 자동 반영하지 않습니다. 텍스트와 이미지 입력 구성 및 JSON 구조는 모의 응답으로 검증했고, 실제 OpenAI 호출은 로컬 키가 없어 미검증입니다.
- 판매계획의 오류·검토 행을 원본 헤더·셀값·사유와 함께 별도 검토 카드로 표시하고 `이 행 제외` 버튼을 추가했습니다. 제외 결정은 DB의 원본 행·표준화 결과에 사유와 함께 저장되며 새로고침 후 다시 조회됩니다.
- 실제 HTTP와 PostgreSQL로 확인 필요 행 생성→사용자 제외→상태 및 수량·금액 대사 재계산→정상 1행만 Sales Master 반영→검증 주문·배치 완전 삭제 흐름을 통과했습니다. Python 컴파일과 Next.js 프로덕션 빌드도 통과했습니다.

## 2026-11-04 생산정보 기반 생산사이트 자동 매칭

- 직전의 판매계획 `원본 컬럼 연결/생산법인 일괄 적용` UI와 공통값 저장을 철회했습니다. 판매계획의 한 파일·한 판매법인 안에도 여러 생산사이트가 있을 수 있어 사용자가 하나를 지정하지 않습니다.
- Alembic `0018`로 일괄값 컬럼을 제거하고, 생산정보가 아직 연결되지 않은 주문은 생산법인을 비워 둘 수 있게 했습니다.
- 생산정보의 PO·모델·행별 판매법인으로 주문 후보를 좁히고 후보가 하나이며 기존 연결과 새 생산수량의 합이 주문 수량 이하일 때만 생산법인과 PST를 연결합니다. 당시에는 모든 행을 `예정`으로 연결했으나, 2026-11-06 업무 규칙 변경으로 프로젝트 기준 날짜보다 과거인 PST는 `실제 완료`로 표시합니다. 모호한 후보·생산법인 충돌·수량 초과·수동 우선값은 자동 확정하지 않습니다.
- 생산정보가 판매계획보다 먼저 업로드되어도 판매계획의 `Sales Master에 반영` 시 프로젝트의 생산정보를 다시 처리합니다. 같은 생산 원본 재처리는 그 원본의 자동 연결만 교체해 중복을 막습니다.
- 실제 PostgreSQL 트랜잭션에서 생산사이트 없는 판매계획 표준화와 PO `00047120`·모델이 같은 6ea+4ea 생산정보의 생산법인·PST 자동 연결 및 합계 10ea를 확인했고 테스트 자료는 rollback했습니다. Python 컴파일과 Next.js 프로덕션 빌드는 통과했습니다. 실제 사용자 파일의 판매계획 반영 후 브라우저 확인과 API 키를 사용한 AI 헤더 호출은 미검증입니다.


## 2026-11-04 업로드 이력 Sales Master 매칭

- 미반영 판매계획의 업로드 이력 관리 열에 `Sales Master 매칭` 버튼을 추가했습니다. 누르면 저장된 원본 바이트를 다시 읽어 시트·헤더 선택 화면을 열고 해당 위치로 자동 이동합니다.
- 반영 완료 또는 버전 비교 대기 판매계획은 중복 처리를 막기 위해 버튼 대신 `매칭 처리 완료`를 표시합니다. 생산·선적정보와 비정형 입력에는 이 버튼을 표시하지 않습니다.
- 인증과 현재 프로젝트 소속을 확인하는 원본 재열기 API를 추가했습니다. 실제 HTTP에서 저장된 XLSX의 같은 배치 ID와 시트 목록을 다시 받은 뒤 기존 표준화·반영·삭제 회귀 검사를 통과했습니다.


## 2026-11-04 생산·선적 업로드 생산법인 및 프로젝트 법인 추가

- 생산정보와 선적정보 모두 특정 판매법인을 선택하지 않고 `파일 내 여러 판매법인`으로 등록합니다. 두 유형에는 생산법인 토글을 추가했고 이집트·인도네시아·구미를 앞에 배치하며 기존 생산법인과 직접 추가한 생산법인도 이어서 선택할 수 있습니다.
- 업로드 이력에 생산법인 열을 추가했습니다. 판매계획은 기존처럼 판매법인을 선택하고, 생산·선적정보는 생산법인을 필수로 선택합니다.
- 판매법인과 생산법인을 화면에서 직접 추가하는 API·입력 영역을 만들었습니다. 추가 법인은 현재 프로젝트에만 보이고, 같은 유형·이름의 중복을 차단합니다.
- 프로젝트 사본은 프로젝트 전용 법인을 새 내부 ID로 복제해 주문 연결을 바꾸며, 프로젝트 영구 삭제는 종속 주문·업로드 이후 그 프로젝트의 직접 추가 법인을 정리합니다.
- Alembic `0016`으로 법인의 프로젝트 소속과 업로드 배치의 생산법인 연결을 추가했습니다. 실제 HTTP에서 프로젝트 전용 판매·생산법인 추가, 생산·선적 XLSX의 복수 판매법인 처리, 기본·직접 추가 생산법인 저장, 이력 조회와 영구 삭제를 확인했습니다. 검증 법인·배치·원본은 모두 정리했고 Python 컴파일과 Next.js 빌드를 통과했습니다.

## 2026-11-04 복수 판매법인 생산정보 업로드

- 생산정보 파일은 한 생산법인이 여러 판매법인의 제품을 함께 포함할 수 있으므로 판매법인 선택을 제거했습니다. 화면에는 수정할 수 없는 `파일 내 여러 판매법인` 범위를 표시하고, 판매계획·선적정보는 기존처럼 판매법인을 필수로 선택합니다.
